既然 `sfsEdgeStore` 已经能完美地“接住”数据了，那现在的关键就是**怎么让 EdgeX 动起来去“抓取”数据**。

在 EdgeX Foundry 里，这个过程叫**“设备接入”**，核心全靠**设备服务（Device Service）**。你不需要写代码去连 PLC 或传感器，EdgeX 官方和社区已经提供了现成的“驱动”。

你只需要通过 **API** 告诉 EdgeX：“我要连什么设备”、“设备在哪”、“数据怎么读”。

下面我手把手教你，怎么通过 **3 个步骤**，配置 EdgeX 去采集数据（以最常见的 **Modbus TCP** 协议为例，比如连一个温控器或 PLC）：

### 📦 第一步：准备好“驱动”（设备服务）

EdgeX 本身只是一个框架，它需要插件来连接硬件。
你需要启动一个 **Modbus TCP 设备服务**（官方叫 `edgex-device-modbus`）。

- **怎么做：** 在你的 `docker-compose.yml` 文件里，把 `device-modbus` 服务的注释去掉，让它和 `core-data` 等服务一起启动。
- **作用：** 这个服务就像一个“翻译官”，它专门负责说 Modbus 语言。

### 📝 第二步：定义“数据字典”（Value Descriptor / Device Profile）

EdgeX 需要知道你要采集的数据长什么样（是整数？还是浮点数？叫什么名字？）。

你需要创建一个 **设备配置文件（Device Profile）**。这是一个 YAML 文件，用来描述设备。

**举个例子（`modbus-profile.yaml`）：**
```yaml
name: "Temperature-Sensor"
manufacturer: "MyFactory"
model: "Temp-V1"
labels:
  - "modbus"
  - "temperature"
description: "温度传感器配置"

# 定义采集的数据项
deviceResources:
  - name: "CurrentTemp"       # 数据在 EdgeX 里的名字
    description: "当前温度"
    properties:
      valueType: "Float32"    # 数据类型
      readWrite: "R"          # 只读
      # 定义 Modbus 寄存器地址
      attributes:
        PrimaryRegisterAddress: "100" # 寄存器地址
        PrimaryRegisterType: "InputRegister"

# 定义采集指令
deviceCommands:
  - name: "GetTemp"
    readWrite: "R"
    resourceOperations:
      - CurrentTemp
```

### 🔗 第三步：添加“设备实例”（Device）

有了“驱动”和“字典”，最后一步是把具体的设备加进去。比如你的 PLC IP 是 `192.168.1.100`。

你需要调用 EdgeX 的 **Core Metadata API** 来注册这个设备。

**操作方法（使用 curl 命令）：**

```bash
# 1. 先添加设备配置文件 (上传刚才的 yaml)
curl -X POST -H 'Content-Type: application/yaml' \
     --upload-file modbus-profile.yaml \
     http://localhost:59880/api/v1/deviceprofile

# 2. 添加具体的设备实例
curl -X POST -H 'Content-Type: application/json' \
     -d '{
  "name": "PLC-001",              // 设备名字
  "serviceName": "device-modbus", // 使用哪个驱动
  "profileName": "Temperature-Sensor", // 使用哪个配置文件
  "protocols": {
    "modbus": {
      "Address": "192.168.1.100", // 设备 IP
      "Port": "502",              // 端口
      "UnitID": "1"               // 从站 ID
    }
  },
  "autoEvents": [                 // 自动采集配置
    {
      "interval": "1s",           // 每 1 秒采集一次
      "onChange": false,
      "resource": "GetTemp"       // 采集哪个命令
    }
  ]
}' \
http://localhost:59881/api/v1/device
```

### 🚀 结果：数据自动流转

一旦你执行完上面的配置：

1.  **EdgeX** 会根据 `autoEvents` 的配置，每 1 秒钟通过 Modbus 协议去问 `192.168.1.100`：“温度是多少？”
2.  **EdgeX** 拿到数据（比如 25.5），把它包装成标准事件。
3.  **EdgeX** 把事件扔到消息总线。
4.  **sfsEdgeStore** 监听到消息，瞬间把 `25.5` 存入 LevelDB。

### 📌 总结

**你不需要写代码去连设备。**
你只需要：
1.  **启动** 对应的设备服务（Modbus, OPC UA, MQTT 等）。
2.  **配置** 设备的 IP 和寄存器地址（通过 API）。

剩下的，EdgeX 会自动帮你跑腿，你的 `sfsEdgeStore` 只需要负责收货就行。这就是 EdgeX 最大的价值——**把复杂的硬件连接变成了简单的配置工作。**

但这并不意味着你要写很多复杂的代码。在 EdgeX 的设计哲学里，这叫**“声明式配置”**。你只需要准备好两份“说明书”，然后通过 API 告诉 EdgeX 就行了。

为了让你更清楚怎么操作，我们把配置过程拆解为**“通用模板”**和**“个体档案”**两部分：

### 📂 配置的核心逻辑：两类“说明书”

#### 设备配置文件 —— “通用模板”
**（对应 EdgeX 的 `Device Profile`）**

- **这是什么：** 它是给**同一类**设备用的。
- **场景：** 假设你现场有 10 个**相同型号**的温度传感器（比如都是“华为 Temp-V1”）。
- **你要做什么：** 你只需要写**一份** YAML 文件，定义好：
    - 这个设备有哪些数据（温度、湿度）。
    - 这些数据在寄存器里的地址是多少（比如温度在地址 100）。
    - 数据格式是什么（是整数还是浮点数）。
- **结论：** **同一种型号的设备，共用这一份配置，不用重复写。**

#### 设备实例配置 —— “个体档案”
**（对应 EdgeX 的 `Device`）**

- **这是什么：** 它是给**每一个具体的**设备用的。
- **场景：** 还是那 10 个温度传感器。虽然型号一样，但它们的**IP 地址**或**串口连接方式**不一样。
    - 设备 A：IP 是 192.168.1.10
    - 设备 B：IP 是 192.168.1.11
- **你要做什么：** 你需要为这 10 个设备分别调用 API，告诉 EdgeX：
    - “这是设备 A，它的 IP 是 xxx，它套用上面的‘通用模板’。”
    - “这是设备 B，它的 IP 是 yyy，它也套用上面的‘通用模板’。”
- **结论：** **每一个物理设备，都需要一个独立的“个体档案”。**

### 🛠️ 实际操作：如何高效配置？

虽然听起来要配两次，但在实际工程中（尤其是你卖网关盒子），我们有**“批量化”**的玩法：

#### 1. 针对“不同协议”的设备
EdgeX 是模块化的，**不同的协议需要启动不同的“设备服务”**。
- **Modbus 设备：** 启动 `device-modbus` 服务，配置 Modbus 的 Profile。
- **OPC UA 设备：** 启动 `device-opcua` 服务，配置 OPC UA 的 Profile。
- **MQTT 设备：** 启动 `device-mqtt` 服务，配置 MQTT 的 Profile。
- **你的工作：** 在网关的 `docker-compose.yml` 里把对应的服务打开，然后分别配置。

#### 2. 针对“大量相同设备”
如果你要接 100 个一模一样的传感器，你不需要写 100 个 API 请求。
你可以写一个简单的 **Shell 脚本** 或 **Python 脚本**，放在你的网关盒子里：
- 脚本里写好循环：IP 从 `.1` 到 `.100`。
- 脚本自动调用 EdgeX API 批量注册这 100 个设备。
- **结果：** 一键执行，100 个设备全部配置完成。

### 💡 你的网关产品优势在哪里？

既然配置这么麻烦，**这正是你卖 3000 元网关的价值所在**：

1.  **预置配置：**
    你可以针对市面上主流的 PLC（西门子、三菱、欧姆龙），提前写好标准的 **Device Profile (YAML)**，预装在网关里。
2.  **简化操作：**
    客户拿到网关，不需要手写 YAML。你可以做一个简单的**网页界面**（或者命令行向导）：
    - 客户选：“我要接西门子 S7-1200”。
    - 客户填：“IP 是 192.168.1.50”。
    - **你的网关后台自动调用 EdgeX API 完成配置。**

### 📌 总结

- **不同型号的设备** -> 需要写不同的 **配置文件 (YAML)**。
- **不同个体的设备** -> 需要注册不同的 **设备实例 (API)**。
- **不同协议的设备** -> 需要开启不同的 **设备服务 (Docker)**。

虽然看起来繁琐，但这是工业物联网的标准做法（解耦）。对于你来说，**把这些繁琐的配置封装成“一键脚本”或“预设模板”**，就是你的核心竞争力。


### 示例

**千万别为每个客户都写一个脚本，那你就会陷入“外包公司”的死循环——代码越堆越乱，最后全是 `if customer == "A"` 这种没法维护的烂代码。**

解决这个问题的核心思路是：**“配置化”而非“代码化”**。

你要做的不是“开发新脚本”，而是**“写一套通用的脚本”**，然后通过**“填表（配置文件）”**来满足客户的不同需求。

这里有 3 个层级的解决方案，帮你把“定制化”变成“标准化”：

### 🛠️ 第一层：用“参数”代替“改代码”（最基础）

你的 `add_device.sh` 脚本不应该写死任何业务逻辑，而应该是一个**通用的执行器**。

**错误的各种脚本：**
- `add_siemens_for_customer_A.sh` （客户A要西门子，采集温度）
- `add_omron_for_customer_B.sh` （客户B要欧姆龙，采集压力）

**正确的一个脚本：**
- `add_device.sh` （万能脚本）

**怎么实现？**
利用脚本的**参数**。
- **客户A的需求：** 采集温度。
    - 命令：`./add_device.sh --name "Temp-Sensor" --ip "192.168.1.10" --template "temp_profile.yaml"`
- **客户B的需求：** 采集压力。
    - 命令：`./add_device.sh --name "Press-Sensor" --ip "192.168.1.20" --template "press_profile.yaml"`

**结论：** 脚本本身不需要动，只需要换**参数**和**模板文件**。

### 📄 第二层：用“配置清单”代替“命令行”（进阶）

客户可能一次要接 50 个设备，敲 50 次命令也累死人。这时候，你要引入**“批量配置清单”**（比如 `devices.csv` 或 `devices.json`）。

**做法：**
你给客户一个 Excel 或者 CSV 模板，让他填好：

| 设备名称 | IP地址 | 设备型号 | 采集频率 |
| :--- | :--- | :--- | :--- |
| 1号电机 | 192.168.1.10 | Siemens-S7 | 1s |
| 2号电机 | 192.168.1.11 | Siemens-S7 | 1s |
| 温控表 | 192.168.1.50 | Omron-E5 | 5s |

**然后，你只需要一个通用的“导入脚本”：**
```bash
# 这个脚本永远不需要修改
./import_devices.sh devices.csv
```

**脚本内部逻辑：**
读取 CSV 每一行 -> 自动匹配对应的 YAML 模板 -> 自动调用 EdgeX API。

**优势：** 无论客户有 1 个设备还是 1000 个设备，无论客户是谁，你都是**同一套代码**，只是**输入文件不同**。

### 🧩 第三层：用“元数据”驱动（终极方案）

这是 Harness Engineering 等现代软件工程的做法。

如果客户A要求“每 1 秒采集一次”，客户B要求“每 5 秒采集一次”，你不需要改脚本，你只需要在**设备配置文件（YAML）**里改一个数字。

**你的工作流应该是这样的：**

1.  **建立“模板库”：**
    你在网关里预置一个文件夹 `/templates/`，里面放好 20 种常见设备的配置（西门子、三菱、施耐德...）。
2.  **客户定制 = 选择模板：**
    客户A说：“我要接西门子”。
    你（或客户）在配置界面选择 `siemens_s7.yaml`。
3.  **客户定制 = 修改参数：**
    客户A说：“我只要温度，不要压力”。
    你在配置界面把“压力”的采集开关关掉（或者在 YAML 里注释掉）。

**结果：**
- 客户A生成了一份 `customer_A_config.yaml`。
- 客户B生成了一份 `customer_B_config.yaml`。
- **你的网关系统（脚本）是完全一样的，只是加载了不同的配置文件。**

### 💡 总结：如何避免“累死”？

| 需求差异点 | 错误做法（累死） | 正确做法（配置化） |
| :--- | :--- | :--- |
| **设备型号不同** | 写不同的脚本 | 准备不同的 **YAML 模板文件** |
| **IP地址不同** | 改脚本里的 IP | 脚本读取 **CSV/JSON 列表** |
| **采集频率不同** | 改脚本里的逻辑 | 修改模板里的 `interval` 参数 |
| **数据项不同** | 删减代码 | 在模板里开启/关闭 **资源开关** |

**你的核心资产不是“给客户写的脚本”，而是你手里积累的“设备模板库”。**

以后来了新客户，你只需要：
1. 从库里挑一个最接近的模板。
2. 改几个参数（IP、端口、频率）。
3. 运行那个**万年不变的通用脚本**。

这就是**“产品化”**和**“项目外包”**的区别。
